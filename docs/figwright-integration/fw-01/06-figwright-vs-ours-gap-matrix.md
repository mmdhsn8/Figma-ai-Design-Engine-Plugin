# 06 — Figwright versus our engine: gap matrix

Source references below are pinned to Figwright v0.8.0 commit 458e3dfa5da5d5c53f1fd5334a35754ffb2a66ca. Local references are from plugin commit 639fdb4f432429ca0dccda3652677a84a4374769. Every behavioral claim in this table is SOURCE evidence unless explicitly marked live; there is no live evidence in FW-1 yet.

| Area | Figwright source behavior | Current plugin source behavior | Category | Pain point and measurable hypothesis / risk |
|---|---|---|---|---|
| Batch semantics and partial failure | packages/mcp/src/tools/batch.ts accepts ordered, schema-checked write operations and references to earlier results such as $0. packages/plugin/src/handlers/batch.ts snapshots supported inverses before applying sequentially, rejects operations it cannot faithfully undo, and reports rollback residue. packages/plugin/src/idempotency.ts deduplicates retries by request ID with a 60-second default cache. | src/ui/universal-design-task.ts checkpoints each validated program before dispatch, bounds repair/render attempts, and assigns stable screen identity. src/plugin/renderer.ts renders one typed screen transaction at a time, stores transaction/idempotency metadata, tracks ownership, and reads back before marking a screen complete. This is not the same public arbitrary-operation batch API. | ALREADY HAVE EQUIVALENT for screen-level identity/rollback safety; INSUFFICIENT EVIDENCE for dispatch-count benefit | Existing weak point to test: native dispatch count and partial-failure recovery across 3 screens. Hypothesis for a future scoped batch spike: reduce MCP/native dispatches per screen without increasing duplicate roots, rollback residue, or unrelated changes. No run evidence justifies a port. |
| Auto Layout and sizing | skills/figma-build/references/write-rules.md and assemble-screens.md guide auto layout for related children, parent-first append, HUG/FILL/FIXED sizing, component reuse, and screenshot/readback confirmation. set_auto_layout and set_layout_props expose those native controls. | src/shared/design-program.ts and design-program-adapter.ts model typed layout; src/plugin/renderer.ts maps HUG/FILL/FIXED through mapSizingMode/mapLayoutSpec, handles RTL layout and vertical mobile scrolling; native verification checks actual bounds and overflow. | ALREADY HAVE EQUIVALENT at source level; live host geometry INSUFFICIENT EVIDENCE | No Desktop bounds were measured. | Native readback and screenshots | packages/mcp/src/tools/get-node.ts, get-document.ts, and get-screenshot.ts expose readback; figma-build calls for visual comparison and bounded corrections. | src/plugin/native-design-verification.ts verifyNativeDesign performs fresh native root lookup and bounded tree checks. The examined Universal route has automated structural/geometry/contrast checks, but no verified automatic screenshot-to-model correction loop was established by this source audit. | ADOPT PATTERN for evidence collection; product-loop result INSUFFICIENT EVIDENCE | Current visual-quality concern is sparse or unprofessional output despite structural validity. Hypothesis: screenshot + readback review will expose unresolved visual defects that structural QA alone misses, with review coverage recorded per completed screen. No aesthetic improvement has been measured. |
| Components and styles | figma-build first reads variables, local/library components, and styles; it instances matching components, binds variables/styles, and creates new assets only when missing. | src/plugin/design-system/component-registry.ts and renderer.ts create/reuse components owned by the current DesignProgram design-system identity and reuse native styles. The inspected flow does not establish that arbitrary existing page/library components are discovered and instanced for every Universal creation. | INSUFFICIENT EVIDENCE | F1 in a clean file has no pre-existing component library, so it cannot fairly measure reuse advantage. A separate seeded design-system fixture would be needed before claiming benefit. Hypothesis: more linked instances and fewer rebuilt primitive nodes without master drift. |
| Connection and file routing | packages/mcp/src/relay/session.ts and election modules implement plugin reconnect/session resume and leader/follower handover. list_files and use_file allow an MCP process to claim an exact connected file/session. Write retries retain request identity. | src/companion/server.ts and src/ui/companion-client.ts provide the local Companion boundary and streaming/request identity. Universal native dispatch remains serialized by the plugin's task/controller state; checkpoints carry task and native ownership identity. | INSUFFICIENT EVIDENCE | File claims can help isolate concurrent MCP clients but also create a second writer path. No product need is established to add another relay or checkpoint ledger. Future benefit hypothesis: zero cross-file writes in two-open-file fault tests; risk is ambiguous ownership if claims and the existing controller diverge. |
| Visual QA workflow | figma-build calls get_screenshot on each constructed section/screen, corrects discrepancies, and re-screens. Guidance explicitly says a successful tool result is not proof. | Existing source provides semantic/contrast preflight, native geometry verification, and readback. Live screenshots and human scores remain required by the product rubric but were not captured in current runs. | ADOPT PATTERN for this benchmark; DEFER production correction loop | Measure visual rubric and unresolved defects per screen before/after one bounded screenshot-guided correction. Require no extra duplicate roots or unrelated changes. Source guidance alone does not establish better quality. |
| Model tool surface and throughput | packages/mcp/src/tools/registry.ts registers the documented 147-tool surface; tools span direct native reads and writes. batch can reduce multiple writes to one MCP call, while the agent/client still decides how many model rounds to use. | The existing Universal path documents 1 intent + 1 plan + N screen programs (3/5/12 calls for 1/3/10 screens before bounded corrections) and converts typed DesignProgramV1 documents to native writes. | INSUFFICIENT EVIDENCE | MCP tool count is not model-call count or latency. Hypothesis: compare valid end-to-end time and separately measured provider wait, tool calls, native batches, and QA. Do not claim a faster path from 147 tools or local request count. |
| Security, license, and runtime | Figwright source is MIT. Its separate plugin manifest permits broad network domains for user-provided image URLs; the MCP server uses localhost relay security checks. Tool calls can write/delete nodes, pages, variables, styles, and other design data. | The existing plugin manifest allows no network domain in production and localhost:1455 only for development. The Universal Engine passes typed, validated design data to a native renderer; no arbitrary model-generated JavaScript is part of the audited path. | REJECT unrestricted execution/destructive relay; PORT CODE AFTER LEGAL REVIEW only if later justified | Any copied code needs preserved MIT notice, a transitive dependency license inventory, security review, and rollback. Canvas/tool results may be returned to the operator's chosen model client; synthetic data and approved providers are required. |

No transfer of source code is recommended in FW-1. Existing typed rendering, bounded retries, transaction identity, and native readback are material equivalents to several claimed benefits. Screenshot-guided visual review is the strongest distinct source-level candidate, but it is a workflow hypothesis pending live proof.
