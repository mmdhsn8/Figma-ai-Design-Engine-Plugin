# FW-3 — failure and recovery matrix

The planner-only path cannot encounter native mutation crash windows because it never dispatches its plan. This matrix states the safe policy for any future batch executor and identifies what the current renderer already does. It is not a claim that FW-3 has implemented batch execution, rollback or task-owner integration.

| Window / event | Observable state | Legal next action | Retry / root-count rule |
|---|---|---|---|
| 1. Before batch dispatch | Existing canonical program/checkpoint; no FW-3 native mutation. Current owner has saved the program and marks the screen rendering before its single render request. | Revalidate active task, page, screen, fingerprint, root and checkpoint immediately before mutation. | Retry only same transaction after revalidation; no new root until original recorded identity is looked up. Current renderer uses existing root identity checks. |
| 2. After root creation, before attachment | A newly created unattached temporary node may exist; no attached screen root is established. | Record real ID. A future adapter may remove only a provably batch-owned unattached temporary node, and must report cleanup failure. | Reconcile that ID before another create. Never guess that a missing response means no creation. Current renderer policy is retained; FW-3 has no batch temp-node adapter. |
| 3. After attachment, midway through children | Attached task-owned root and partial children may remain. Current renderer sets the root receipt as part of preparation and uses `preserveFailedProgramNodes`. | Keep root/children and IDs; mark screen incomplete, record op failure, inspect/reconcile original root. | Do not delete/recreate root. Retry only operations proven idempotent; otherwise stop for inspection. Root count must remain one. |
| 4. Mutations finished, before readback | Native tree may be complete, but geometry/properties have not been confirmed. | Read back original root with a bounded inspection. | No verified status and no new root. Timeout means uncertain, then reconcile the original ID. |
| 5. Readback finished, before checkpoint ack | Native root may be fully verified while UI checkpoint is behind. Existing task status can still be `rendered` or `rendering`. | Re-read current task generation, verify receipt identity and write the verification into the one existing checkpoint owner. | Duplicate/lost ack reuses same root and native receipt; do not repeat creates. Old-generation acknowledgement is ignored by current task identity/fencing. |
| 6. During checkpoint read-after-write | Save may have failed or be uncertain; attached native nodes remain. | Stop next writes, reread canonical checkpoint, reconcile existing root and native adoption record. | Do not advance screen status based on an unconfirmed save. No replacement root. |
| 7. Stop while sibling preparation finishes | Current scheduler may still have model preparation settling; no later screen may mutate after task stop/failure. | Abort/fence sibling preparations and late replies; retain current attached/confirmed roots and IDs. | Stop issues no new render requests. Existing serial owner and abort checks remain. A future batch must check task generation/state immediately before every mutation. |
| 8. Plugin restart; user moved/deleted root | Checkpoint points to original root ID; lookup returns missing, removed, or wrong page/parent. Current renderer fails `native_root_missing`, `native_root_removed` or `native_root_moved_or_retagged` and does not create a replacement. | Ask for explicit user recovery/inspection. | Fail closed. Never reparent or silently recreate. Root count cannot increase by automatic retry. |
| Lost/delayed ack, duplicate/reordered message | Request may have been applied although UI did not receive the response. | Correlate by existing request ID, task generation, screen, fingerprint and root ID; inspect original root first. | Late/stale acks cannot commit a newer task. No replay of non-idempotent creation until reconciliation proves it safe. |
| Readback throws or times out | Application is uncertain; attached root may exist. | Read back the same ID again with bounded coverage. | No verified receipt; no replacement root. |
| Explicit partial rollback/cleanup failure | Some prior operations or nodes may remain. Upstream Figwright also reports residual state when reverse restore fails. | Preserve evidence and all attached roots; include per-op cleanup errors. | No “atomic” claim. Only safe un-attached temporaries may be compensated. |

The regression `retains the attached 01 — Welcome root after geometry verification fails` directly verifies attached root, children and unrelated-node preservation on the current renderer path. `src/plugin/design-program-spike.ts` uses `preserveFailedProgramNodes: true`; FW-3 did not add any cleanup path. Full native fault injection for the listed batch executor remains unimplemented and is a required gate before any future integration.
