# Persisted reference-alias collision — root cause and acceptance gate

**Status:** automated and scripted acceptance pass, including the `inspect_nodes`, planning-round, saved-plan, capacity-accounting, and native-parenting fixes; authenticated Figma Desktop acceptance is **BLOCKED** until the post-fix manual run succeeds. No Phase 5.9 work or production-readiness claim is included.

## Evidence boundary

- The source path and a persisted-state regression reproduce the reported `ambiguous_alias` failure. The regression was run against the old resolver and failed there; it passes after the resolver change.
- The reproducer is synthetic: it creates a page-global `store_mobile` reference, inspects it from a task, creates a task-owned node under the same alias, saves a checkpoint after one committed mutation, reloads it, recreates the executor, and resumes. It is not evidence that the live document had this exact owner or history.
- The exact live owner of `store_mobile`, the original rejected operation, and the live checkpoint contents remain unknown until sanitized diagnostics are supplied. Do not infer them from the fixture.
- The separate planning-metadata rejection documented in [phase-5-8-stability-gate.md](phase-5-8-stability-gate.md) is not proof of this resolver failure or its cause.

## Root cause

The application maintains two related but distinct stores: page-scoped native-node references in the tool executor, and a document/page-scoped chat-task checkpoint. An existing page node can already have the literal reference `store_mobile`. When a task inspects it, `registerLogicalRef` records that it was inspected by that task. A new task-owned creation using the same alias receives a task-scoped canonical reference and stores the alias separately.

On a later operation, `resolveTaskAction` finds the unique current-task alias and the same-literal page reference. The old resolver threw `ambiguous_alias` when that page reference had also been inspected by the current task, even though the task-owned alias mapped to one canonical reference. The failure occurred before the action reached the native-node resolver; a safe, already-created task node was therefore mistaken for an ambiguous target. A one-operation checkpoint could persist this state, so reload/resume repeated the same failure.

The resolver now treats a **unique current-task alias mapping** as authoritative over a same-literal page reference. It still validates the canonical reference against persisted page/node identity before targeting anything. Multiple current-task nodes with the same alias remain ambiguous and fail closed.

## Follow-up hotfix: `inspect_nodes.maxNodes`

The supplied live screenshot showed an authenticated Responses call rejected at `arguments.maxNodes` with `arguments_schema/too_big`, after 1 of 3 stages and 31 confirmed mutations (17 model rounds, 19 batches). The screenshot establishes that the value was numeric and above 25, but does not show the scalar; the sanitized diagnostic did not retain it, and its exact historical value is unavailable. Do not infer a value.

The authenticated `/v1/chat` route sends `CHAT_FUNCTION_TOOLS`, generated from the same strict `FigmaToolActionSchema` used to parse calls. The tool schema advertises `maxNodes` as an integer 1–25 (default 25), `depth` as 0–4 (default 2), and at most 20 refs. The parser now clamps only finite numeric values outside the read-only inspection bounds before strict validation; missing values still use schema defaults. It does not coerce strings, booleans, nulls, or in-range fractions. Native inspection output remains capped at 25 nodes. Invalid values return the exact accepted range and safe type/finite-number diagnostics without echoing full arguments.

The regression in `tests/companion-server.test.ts` verifies the authenticated Responses schema, local clamping, and a storage-backed three-stage Stop/Resume/Retry path. It commits 31 native mock nodes, reloads the checkpoint, inspects between stages, injects a pre-commit stage-three failure, retries only that stage, and verifies the same 31 node IDs remain with no duplicate stage frames. This is automated simulated acceptance, not a new live Desktop run.

## Follow-up live failure: planning budget exhaustion

After the inspection hotfix, an authenticated Desktop run for two Persian clothing-store screens stopped with 0/2 stages complete, four confirmed mutations, ten model rounds, eight native batches, and `planning/planning_budget_exhausted`. A partial frame remained visible. This is real Desktop evidence; the historical checkpoint did not record each model-round or batch category, so the exact split between mutations, inspections, retries, and acknowledgements cannot be reconstructed.

The source root cause is deterministic: `runChatTask` incremented `current.rounds` for every completed model response and refused another model call at eight. Once a plan existed, successful mutation turns, read-only inspections, schema corrections, premature prose completion, and the final `complete_canvas_stage` turn all consumed the same per-stage “planning” counter. A screen-sized stage could therefore make native progress and still stop immediately before local verification. The UI also labeled every active-stage request “Planning”, hiding the distinction.

The fix does not raise that retry budget. It removes the incorrect per-stage planning gate and retains the 100-turn task ceiling, four-turn pre-plan ceiling, validation/reference correction limits, and no-progress termination. Persisted lifecycle counters now separate pre-plan, planning, execution, inspection, completion, correction, continuation, and model transport retries. Successful execution acknowledgements no longer consume a planning budget. Repeated plans cannot replace a saved plan; repeated identical inspections with no intervening mutation reuse the prior bounded result locally, and another no-progress repeat stops. Stage completion still requires confirmed mutations, every declared acceptance ref, and deterministic native geometry, visibility, text, Auto Layout, clipping, and contrast inspection. Missing refs and quality findings are returned specifically before the stage advances.

Automated regressions reproduce the old boundary: the Home stage performs four confirmed mutation turns and four intervening inspection turns, then completes on its ninth stage model turn instead of failing before completion. A real-executor test stops after four commits, reloads, preserves their node IDs, completes editable RTL Home and Product screens with Auto Layout, and changes an existing purchase button without adding a node or changing the header. This is simulated Figma API/model evidence only.

## Follow-up live failure: saved-plan re-entry

The next authenticated Desktop run stopped with 0/2 stages, zero confirmed mutations, six model rounds, three batches, and `no_progress_repeated_error: planning/plan_already_saved`. The plan had been persisted, but the authenticated Responses request still advertised `plan_canvas_task` on every continuation. The runner treated the first duplicate as a planning failure and the next identical duplicate as no progress, so execution tools were never reached.

The checkpoint now has an explicit lifecycle: `UNPLANNED → PLAN_SAVED → EXECUTING_STAGE → VERIFYING_STAGE → STAGE_COMPLETED → TASK_COMPLETED`. Every authenticated `/v1/chat` request carries that validated state. `plan_canvas_task` is advertised only in `UNPLANNED`; saved/executing states receive only their applicable mutation, inspection, status, and completion tools. If an upstream model nevertheless emits planning after a saved plan, the server marks it as a state redirect and the runner returns the immutable canonical plan, current position, and next stage. It does not overwrite stages, reset operation IDs, increment validation corrections, or trigger `plan_already_saved`.

The Responses continuation regression intentionally emits a valid multi-stage plan and then a second planning call. It verifies that the post-plan upstream request no longer exposes planning, the duplicate is locally redirected, native execution begins, no correction round is consumed, and the existing Stop/Resume/Retry and no-duplicate assertions still complete. State-transition tests also require persisted `PLAN_SAVED`, `VERIFYING_STAGE`, `STAGE_COMPLETED`, and final `TASK_COMPLETED` checkpoints.

## Follow-up live failure: mixed task capacity

The latest authenticated Desktop run stopped at 0/2 stages with 25 confirmed native mutations, 18 model rounds, 19 batches, and `Task capacity reached: 32/240 operations, stage 31/32 including read-only verification`. The Home screen was partial and Product was unfinished. The exact historical composition of all 19 batches is unavailable because that checkpoint did not persist operation categories.

The source root cause is direct: `stageOperationCount` counted every stage ledger entry except `get_document_context`, while `task.ledger.length` enforced the 240 task limit. Model inspections, reused inspections, local QA verification, failed reads, and native mutations therefore consumed the same 32/240 counters. A legitimate 25-mutation stage with six inspections reached 31/32 and could not schedule its next call even though only 25 mutation slots had been used.

Accounting is now persisted by category: native mutation, model read-only, and local verification. Model requests, native batches, and lifecycle transitions retain independent persisted counters. The 240 task capacity applies only to mutations. The former 32 mixed-operation stage guard is now a 32-mutation execution-segment boundary: an estimated oversized canonical stage preallocates deterministic segments, and underestimation appends the next segment without replacing the saved plan. Operation IDs remain stable, native batches never cross segment boundaries, a full segment becomes confirmed only from executor acknowledgements, and final required refs plus native structural QA still gate canonical stage completion. Read-only and verification work have separate limits, while ledger entries and the 512 KiB checkpoint remain independently bounded.

The runner regression reproduces the old 31/32 composition with 25 mutations plus six model inspections and completes with 26 mutations instead of failing. Another stage completes 40 mutations as confirmed 32+8 segments. The real executor regression stops after exactly 25 confirmed operations in a 35-mutation Home stage, serializes/reloads the checkpoint, completes Home and Product RTL Auto Layout screens, preserves the first node IDs, creates no duplicate frames/cards/text, and changes only the requested existing purchase button.

## Call path and state boundaries

1. `src/ui/App.tsx` (`sendChatMessage`) builds/resumes the task and checkpoints it through `chatTaskBridge`.
2. `src/ui/chat-task.ts` (`runChatTask`, `chatTaskInput`) manages planning, confirmed calls, operation IDs, retries, and saved continuation state.
3. `src/ui/companion-client.ts` (`streamAuthorizedChat`) sends the authorized turn to `src/companion/server.ts` (`handleChat`, `/v1/chat`). The companion validates Responses function calls and streams `tool_calls` through SSE.
4. `runChatTask` dispatches approved operations to `App.tsx` (`runToolOperations`) as `tool-execute` messages. `src/plugin/main.ts` validates the message with `UIToPluginSchema` and dispatches it to the executor.
5. `src/plugin/figma-tool-executor.ts` runs `executeBatch` → `executeOperation` → `resolveTaskAction` → `actionResult`. `resolveTaskAction` selects a canonical task reference; `resolveRef` verifies the persisted reference and the current Figma page before a native node can be targeted.
6. `src/plugin/chat-task-storage.ts` stores/reloads the checkpoint under the active file/page key. The executor separately persists page-scoped references and operation/idempotency records in client storage; node plugin data binds canonical ref, task, operation, and creation fingerprint.

The Responses/OAuth service and Figma objects in automated tests are controlled mocks. This call path is production code under test, not authenticated live-model or Desktop execution.

## Resolver and safety invariants

- If exactly one current-task mapping exists for an alias, resolve to its canonical reference rather than the same-literal page ref.
- Before editing, `resolveRef` confirms the stored page and node still exist on the current page, the node carries the canonical ref, and the reference remains unique. For records that have the new identity fields it also checks parent, node type, and creation fingerprint; task and creation-operation metadata are checked when present. A targeted `inspect_nodes` can refresh only the observed parent after rechecking the same native identity; ordinary edits still reject stale parent state.
- A stale, moved, changed, missing, foreign-page, unconfirmed, or otherwise uncertain target is not guessed or recreated. A genuinely duplicated current-task alias returns at most three canonical candidates plus the bounded total count and tells the caller to inspect candidates one at a time.
- `parentId` is updated only after an authorized append/reparent operation succeeds and its undo commit is made. An out-of-band move or fingerprint tamper fails closed; a successfully authorized move remains resolvable for later edits.
- The change does not loosen schemas, ownership, page scope, idempotency, deletion consent, cancellation, or retry rules. Existing user-owned content still requires the established inspection path.

## Follow-up live failure: `append_child` and partial-commit accounting

The authenticated Desktop report recorded task `chat-1794036913451-2cuy96`, operation `chat-1794036913451-2cuy96-op-38`, 13 confirmed mutations, 13 failed operations, four required refs remaining, 23 model requests, 22 native batches, and 11 read-only operations. The runner did not rewrite the action. It permits root-to-frame append, acknowledges an already-correct parent as a no-op, rejects implicit cross-parent append, and accepts a move only through explicit `reparent_node` when the saved/current parent state agrees. Stale or duplicated refs and cycles fail closed. For ambiguous interruptions, the persisted operation records its source and target parent IDs; retry resolves the same native node and compares its actual parent before it decides whether to confirm a commit, verify a no-op, retry from the unchanged source, or stop for inspection. It never recreates a node to bypass a parenting error.

The count mismatch candidate is also resolved in source: stage synchronization counted `repaired` ledger entries as confirmed while the task counter counted only completed, non-reused operations. ## Follow-up live failure: structural QA and `call_set/too_many_calls`

### Confirmed source causes

- `src/shared/chat-tools.ts:parseResponsesFunctionCalls` emits `stage: "call_set", errorCode: "too_many_calls"` only when the Responses output contains more than ten `function_call` items. `call_set` is the validation stage, not a registered tool name and not an argument-schema field. `CHAT_FUNCTION_TOOLS` and `chatFunctionToolsForState` are the advertised allowlist; the companion's `handleChat` validates the complete response before sending any `tool_calls` SSE event. Therefore the reported error confirms an oversized call set was rejected before dispatch, if it came from this running source. The raw response and deployed revision were not supplied, so the exact call count/names and build attribution remain unavailable.
- The API request permits parallel function calls, while the runner accepts at most ten in one response. The previous `CHAT_INSTRUCTIONS` asked for grouped calls but omitted the ten-call response bound. It now states the bound explicitly; supported Responses `function_call` items remain strictly parsed, and an explicit unsupported `type: "call_set"` wrapper is rejected as `unsupported_wrapper`. Embedded calls are never extracted or executed.
- Before this repair, `runChatTask` incremented `repairOperationsExecuted` when a mutation returned success while `awaitingQualityRepair`; it did not inspect after each repair. A successful native acknowledgement therefore meant “the requested setter was accepted,” not “the QA finding was corrected.” A later model-issued completion call caused a fresh `inspect_nodes`, but two ineffective repairs could run first and be counted as executed without before/after evidence.
- `summarizeNode` rounded `x`, `y`, dimensions, and `absoluteBoundingBox` to whole pixels, and omitted transforms, padding, sizing/alignment and child layout-position metadata. The QA request itself used a new native `inspect_nodes` operation and did not read checkpoint geometry, so stale checkpoint geometry is not supported by the code path. The measurement did, however, lose sub-pixel precision and could compare axis-aligned absolute boxes without accounting for rotated, scaled or RTL-transformed local bounds.
- `inspect_nodes` also deduplicated requested roots before assembling their tree. If a stage listed both a parent and its child, the child was returned as its own root; when the parent traversal encountered the already-seen child, it omitted that child from `parent.children`. This source behavior is confirmed and could hide parent-relative clipping in such an inspection. The exact live refs/tree are unavailable, so it is not established as a cause for these specific three findings. The executor now reuses the existing child summary under its parent while retaining the bounded unique-node count.
- `auditNativeSection` used those rounded rectangles for clipping. It reported only parents with `clipsContent`; it did not include the clipping setting's intent or enough layout context to classify Auto Layout overflow versus explicit clipping. The actual node bounds and clip intent in the live file are unavailable, so the three reported clipping causes remain unconfirmed.
- Contrast comparison used the full-precision ratio available from 8-bit hex colors, but both diagnostic fields were rounded with `toFixed(2)`. A failing value just below 4.5 could consequently display as `4.50:1`. `summarizeNode` discarded partially transparent paints, and the audit did not alpha-composite fills/text. The exact unrounded live ratios and native paint stack are unavailable; attribution of either specific live contrast node remains unconfirmed.

### Localized repair and behavior change

- `src/plugin/figma-tool-executor.ts:summarizeNode` now emits unrounded local and absolute geometry, native transforms, Auto Layout sizing/alignment/padding, text alignment and child layout sizing/positioning. Contrast inputs are exposed only for a single measurable visible solid paint; unsupported stacked/gradient paints are not guessed.
- `src/plugin/figma-tool-executor.ts:actionResult`'s `inspect_nodes` tree assembly now attaches an already-requested child summary to the inspected parent, so required-ref deduplication no longer breaks structural ancestry.
- `src/shared/native-visual-quality.ts:contains`, `overflowAmount`, `nativeContrastRatio`, and `auditNativeSection` now compare clipping geometry in the parent's local coordinate space when transforms are available, with a tight floating-point tolerance. Findings include clip state, measured overflow, transform-aware bounds, layout mode, padding, sizing, positioning and a bounded classification. Explicit clipping intent cannot be inferred from geometry alone; the system reports it and fails safely rather than silently moving, resizing, unclipping, deleting or recreating layers. Auto Layout overlap findings ignore explicitly absolute-positioned children and report measured overlap area.
- Contrast uses full-precision composited foreground/background colors and effective opacity for measurable solid paints. The comparison is against the configured 4.5/3.0 threshold before formatting; the diagnostic retains the unrounded ratio and threshold, so a value like 4.499... cannot masquerade as a passing 4.50.
- Inspection also retains Figma's native floating-point RGB channels alongside the compatible 8-bit hex fields. Contrast now uses those original channels when present; this matters because a native color can round to a hex value on the opposite side of the 4.5 threshold. A regression confirms `#8B6F7D` would fail at 8-bit precision while native `r=0.543138` passes. Unsupported paint stacks remain unmeasured.
- `src/ui/chat-task.ts:inspectAfterQualityRepair` now runs a fresh, checkpointed native inspection after each confirmed mutation during structural repair, audits the returned nodes, stores linked before/after findings and repair operation identity, and updates resolved-finding counts. While repairing, only one mutation is accepted per model response. A no-progress measurement stops the repair path immediately; Resume performs a new local read-only QA probe and does not ask the model to repeat the same repair unless native measurements have changed. Existing QA retry limits, mutation budgets, task identity, operation IDs, partial-commit reconciliation, and required-reference gate are unchanged.
- `src/shared/chat-tools.ts:parseResponsesFunctionCalls`, `src/companion/server.ts:handleChat`, and `src/ui/chat-task.ts:runChatTask` preserve whole-response rejection before dispatch. The correction feedback distinguishes an oversized set from an unsupported wrapper and contains only the minimal count/allowlist guidance; no missing arguments or embedded call data are guessed.

### Remaining uncertainty and limits

The source changes address measured precision, missing native metadata, contrast compositing, repair acknowledgement semantics and the immediate verification gap. They do **not** establish that the live repairs targeted the right nodes, whether clipping was intentional, the exact rejected response shape, whether a given color has one measurable solid paint, Persian text shaping, or the actual Desktop layout after recalculation. Local inspection relies on Figma's returned native bounds after each separate plugin operation; Desktop must confirm those bounds settle as expected. No automatic layout/color correction is applied where user intent cannot be proven from native facts.

Automated regressions cover the five-finding QA shape, a failing ratio that rounds to 4.50, a native-float ratio that differs across 8-bit rounding, a 3.61 ratio, alpha compositing, transformed nested RTL/Auto Layout geometry, explicit versus absent clipping, immediate no-progress termination and Resume probing, localized contrast repair with fresh re-inspection, unsupported/oversized Responses call sets, 22 committed mutations across executor reload/Resume, and the existing Home/Product plus existing-button-only executor workflow.
